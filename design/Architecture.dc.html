1. Purpose and scope

Groundwork Training is a public web platform that teaches beginners how to train. It publishes a curated exercise library, generates and stores personal workout plans, records training progress, and sustains itself through donations and an optional paid tier.

In scope for this architecture:

  • User identity, accounts and profile management (CRUD).
  • An administrative back office for exercise, category and content management.
  • Personal plan management — assignment, customization and scheduling.
  • Transactional and scheduled notifications, plus a public contact channel.
  • An editorial blog with public, indexable content.
  • Responsive delivery across mobile, tablet and desktop.
  • Recurring subscription payments for advanced plans.
  • One-off donation payments.

Explicitly out of scope for version 1: native mobile applications, wearable-device integration, video hosting, social features, coach marketplace, and multi-language content.

2. System context

The platform serves three human actor types and integrates with five external systems. No other party writes to our data stores.

3. Container architecture

The platform is deliberately a modular monolith, not a microservice estate. A team of one to three engineers cannot operate a distributed system without spending most of its capacity on operations. Modules are separated by clear internal boundaries so that any one of them — most likely the notification worker — can be extracted later without a rewrite.

5. Data architecture

A single PostgreSQL database holds every persistent entity. Payload CMS writes to the same instance in its own schema, so editorial content and application data share one backup, one migration path and one connection pool.

5.2 The plan customization model

This is the single most important modelling decision in the system, and the one most often got wrong. A user does not "edit the official plan" — a user owns a copy of it.

  1. Editors publish plans with isTemplate = true and no owner.
  2. When a member adopts a template, the platform deep-copies the plan, its days and its items into a new row set owned by that member, recording templateId for provenance.
  3. The member edits their copy freely — swap an exercise, change sets, move a day, add a rest day.
  4. Editing a template afterwards never mutates an adopted copy. Members see a non-blocking "a newer version of this plan is available" prompt.

The alternative — storing a diff against a live template — saves a little storage and costs an enormous amount of correctness. Copy-on-adopt is the correct trade.

5.3 Database management

ConcernApproach
EnginePostgreSQL 16 on Neon. Serverless scale-to-zero for preview branches; a provisioned instance for production.
MigrationsDrizzle Kit, forward-only, one migration per pull request, applied automatically on deploy. Every migration must be safe to run while the previous release is still serving traffic.
BranchingEach preview deployment gets a Neon database branch seeded from an anonymised snapshot. No developer connects to production data.
BackupsContinuous write-ahead-log archiving with 7-day point-in-time recovery; a nightly logical dump retained 30 days in separate object storage.
Restore drillQuarterly, into a scratch branch, timed and recorded. A backup that has never been restored is not a backup.
IndexingCovering indexes on plan_items(plan_day_id, position), set_logs(session_id), measurements(user_id, taken_on); a trigram index on exercise name for search.
Connection handlingServerless functions connect through Neon's pooler; the ORM opens no long-lived pool of its own.
CachingRedis (Upstash) for rate-limit counters and session lookups. Library pages are cached at the edge and revalidated by tag when the CMS publishes.
RetentionTraining data retained while the account is active. Deletion request: user row anonymised, sessions and measurements hard-deleted within 30 days, financial records kept 7 years as law requires.

8.2 Deployment pipeline

Trunk-based development. A pull request triggers lint, type-check, unit tests, an accessibility scan and a Playwright end-to-end run against its preview environment. Merging to main promotes the same build artifact to production. Rollback is an instant alias change to the previous deployment; a database migration that cannot be rolled back must ship as an expand-and-contract pair across two releases.

9. DNS management

The registrar holds the domain; Cloudflare is the authoritative nameserver and the single place any record is changed. Registrar lock and two-factor authentication are mandatory on the registrar account, and the domain is registered for five years to remove renewal risk.

Operating rules. TTL stays at 300 seconds during any migration and returns to 3600 afterwards. DNSSEC is enabled. Records are changed only through a reviewed pull request against the Terraform definition — never by hand in a dashboard, because a hand-edited zone has no history and no reviewer. DMARC starts at p=none for two weeks of report collection, then moves to quarantine, then to reject.

Alerting policy. Three conditions page a human: the site is down, the webhook processor is failing, or the error rate exceeds 2% of requests. Everything else is a daily digest. An alert that fires often and is routinely ignored is worse than no alert.

Free and paid tiers pull the product in opposite directionsHighDecide the commercial position before the pricing page is designed. Recommended: everything in this document free, with an optional supporter tier that adds convenience — not access.
Plan customization scope creepHighShip adoption and single-exercise swapping first. A full drag-and-drop builder is a separate, later milestone.
Platform lock-in to VercelMediumNext.js runs on any Node host. Keep no Vercel-only primitive in the domain layer; cron and queue triggers stay thin HTTP handlers.
Exercise media licensingMediumCommission or license imagery explicitly. Never use unlicensed stock or generated likenesses for instructional content.
Medical liabilityMediumVersioned, explicitly accepted disclaimer. No diagnostic claims. Legal review before launch.
Solo maintainer riskMediumDocumented runbooks, no undocumented manual steps, credentials in shared custody.

13.1 Decisions taken

IDDecisionReasoning
ADR-1Modular monolith over microservicesTeam size makes distributed operations a net loss. Boundaries are enforced in code, not by the network.
ADR-2PostgreSQL over a document storeThe domain is relational throughout; the joins are the product.
ADR-3Payload CMS over a bespoke adminSaves roughly six weeks and delivers versioning, drafts and media handling for free.
ADR-4Copy-on-adopt for plansGuarantees a member's plan never changes underneath them.
ADR-5Stripe-hosted checkoutReduces PCI scope to the minimum and removes card handling from the codebase entirely.
ADR-6Offline-first set loggingGyms have poor signal; a lost session is the fastest way to lose a user.
